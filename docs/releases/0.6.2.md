# kallistors 0.6.2

This patch release makes paired fragment-length sampling reproducible with several threads.

## Changes

- Fix the default paired fragment-length sample for a given input, observation goal and
  thread count. Workers previously read a shared remaining quota when they received a
  buffer and published their observations when they finished, so the buffers that
  contributed depended on worker timing. The realized observation count, the effective
  lengths and every abundance could then change slightly between runs.
- Logical sampling buffers are now numbered in input order. Buffer `i` may keep up to the
  goal minus the observations kept by buffers `1..=i - workers`, which is the quota the
  shared counter gives when workers run in step. A worker records its buffer first and
  waits only for strictly earlier buffers, after finishing its own work.
- Two unit tests check the quota rule under shuffled completion order.

Thanks to David Holtz ([@drbh](https://github.com/drbh)) for finding the problem and
contributing the fix in [#1](https://github.com/deminden/kallistors/pull/1).

## Behavior

- One-thread paired runs and all single-end runs are unchanged.
- Equivalence-class counts are unchanged; sampling affects only the fragment model.
- With several threads the sample can still exceed the 10,000-observation goal, and its
  size still depends on the thread count. It no longer depends on timing.
- Original kallisto keeps its timing-dependent sample, so multithreaded paired abundances
  can differ from one kallisto run as before. `--fragment-length-samples 0` uses every
  qualifying observation and gives a model that is also independent of the thread count.
  See the [fragment-sampling policy](../fragment_length_sampling.md).

## Compatibility

Existing CLI and Rust APIs, kallisto v13 indexes and output schemas remain compatible.
Existing indexes can be reused. See the [compatibility guide](../compatibility.md).

## Benchmarks and previous changes

The existing 0.6.0 benchmark reports remain relevant and retain their recorded protocols
and tool versions. See the [benchmark guide](../benchmarks.md#latest-completed-results)
for the published comparisons and the [0.6.1 release notes](0.6.1.md) for the preceding changes.
